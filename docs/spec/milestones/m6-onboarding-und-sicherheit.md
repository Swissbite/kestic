# M6 Onboarding und Sicherheit

Teil von [backlog.md](../backlog.md).

**Ziel:** Ein Endnutzer richtet sein erstes Backup in 5 Schritten ein, sichert sein Passwort und kommt auf einem neuen Rechner wieder an seine Daten. Abschluss des MVP.

**Voraussetzung:** M2, M3, M4, M5. Ablage gemäss [architecture.md](../architecture.md) §Code-Struktur.

**Version:** Der Meilenstein schliesst mit dem Release `v0.6.0` (nicht `v1.0.0`); `v1.0.0` legt der Maintainer später fest ([decisions.md](../decisions.md), «Version nach M6»).

**Ablauf (Halt vor dem Schlüssel-Schreibpfad):** Vor `M6-S02` hält der Meilenstein an (wie M4 vor dem Restore-Schreibpfad). Der Leitstand prüft Entwurf und Auditor-Bericht zum Schlüssel-Schreibpfad ([architecture.md](../architecture.md) §Schlüsselbehandlung, AC-M6-02-10 bis -14) in der Maintainer-Rolle und schickt dem Maintainer eine kurze Zusammenfassung. Der Agent wartet nicht, sondern arbeitet an anderen Stories weiter; `M6-S02`, `M6-S03`, `M6-S06` und `M6-S10` beginnen erst nach der Freigabe.

**Stories ab M6-S14** sind aus Issues und dem Kickoff vom 2026-11-26 entstanden; jede nennt ihr GitHub-Issue. Die Spec ist die Quelle, die Issues verweisen nur darauf.

## Akzeptanzkriterien

Test-Isolation gemäss [test-strategy.md](../test-strategy.md). Zusätzlich: Secret Service als In-Memory- bzw. Datei-Backend, nur Temp-Repos bzw. lokaler `rest-server`. «Zweite Kestic-Instanz» = Instanz mit eigenem, leerem Satz `XDG_*_HOME`. «Integration» = gegen echtes restic mit Temp-Repo.

**Schlüssel-Schreibpfad (gemeinsame Regeln).** Jeder Ablauf, der Keys im Repo ändert (Kit erzeugen in S02 und S10, Kit erneuern in S03, Verbinden mit der Recovery-Passphrase in S06 und jedes künftige Passwort ändern, FR-41), hält die folgenden fünf Regeln ein ([architecture.md](../architecture.md) §Schlüsselbehandlung). S03, S06 und S10 verweisen darauf (AC-M6-03-6, AC-M6-06-7, AC-M6-10-4) und prüfen sie je mit einem eigenen Test für ihren Ablauf. Jede Regel wird durch einen simulierten Fehler genau an ihrem Schritt geprüft (Fake-restic bzw. Fehlerinjektion im Secret-Fake), nie nur im Normalfall.
- **AC-M6-02-10** (FR-35, FR-39, NFR-08) – *Gegeben* ein Ablauf, der einen Key anlegt und einen alten entfernen will, *wenn* er läuft, *dann* (a) steht im Aufrufprotokoll jedes `key add` vor jedem `key remove`, und (b) wird bei einem Fehler von `key add` kein `key remove` aufgerufen · Test: Integration (Fehler bei `key add` simuliert)
- **AC-M6-02-11** (FR-35, FR-39) – *Gegeben* ein neu angelegter Key, *wenn* der Ablauf weitergeht, *dann* (a) läuft ein echtes `restic snapshots` mit dem neuen Passwort (Datei 0600 gemäss AC-M6-02-9) und liefert Exit 0, bevor irgendetwas entfernt wird, und (b) ruft Kestic bei einem Exit ungleich 0 (simuliert: Key unbrauchbar) kein `key remove` auf, lässt alle alten Keys unberührt und meldet es · Test: Integration (Prüfung scheitert simuliert)
- **AC-M6-02-12** (FR-35, FR-39, F7) – *Gegeben* ein Ablauf, der einen alten Key entfernen will, *wenn* der neue Key geprüft ist, *dann* (a) ist das neue Passwort im Passwortspeicher gespeichert (Alltags-Passwort) bzw. hat der Benutzer das Kit als «sicher aufbewahrt» bestätigt (Recovery-Key), bevor `key remove` läuft, und (b) wird bei scheiternder Speicherung (gesperrter Secret-Fake) bzw. fehlender Bestätigung nichts entfernt und der alte Key bleibt gültig · Test: Integration (Speichern scheitert simuliert) + GUI-Smoke (Bestätigung fehlt)
- **AC-M6-02-13** (FR-35, FR-39, NFR-08) – *Gegeben* ein `key remove`, *wenn* es vorbereitet wird, *dann* (a) liest Kestic unmittelbar davor `restic key list` und vergleicht die Key-ID mit der zu entfernenden, (b) ruft es `key remove` nicht auf, wenn die ID nicht in der Liste steht oder nicht der erwarteten Rolle (alter Alltags-Key bzw. alter Recovery-Key) entspricht (simuliert: Liste ohne die ID, vertauschte ID), und (c) entfernt es nie den Key, mit dem Kestic gerade auf das Repo zugreift (der in `key list` als aktuell gekennzeichnete); der Versuch wird ohne `key remove`-Aufruf abgelehnt · Test: Integration (je Fall simuliert; Kennzeichnung «aktuell» der `key list`-Ausgabe gegen 0.18.0 und die aktuelle Version zu verifizieren)
- **AC-M6-02-14** (FR-35, FR-39) – *Gegeben* ein `key remove`, *wenn* es ausgelöst wird, *dann* (a) bleibt danach mindestens ein Key übrig, für den im selben Ablauf `restic snapshots` Exit 0 geliefert hat, und (b) wird `key remove` abgelehnt, wenn dieser Nachweis fehlt oder scheiterte (simuliert), damit nie der letzte nachweislich funktionierende Key entfernt wird · Test: Integration (Nachweis fehlt simuliert)
